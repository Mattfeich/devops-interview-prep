# «В чём разница между…» — блиц-вопросы с разбором

Формат каждого ответа: первая фраза — то, что говоришь на собесе сразу; дальше — разбор, чтобы пережить добивку «а поподробнее?».

---

## 1. Deployment vs StatefulSet vs PV vs PVC

**Короткий ответ:** это две разные пары. Deployment и StatefulSet — контроллеры запуска подов (взаимозаменяемые копии vs реплики с личностью). PV и PVC — про диски: PV — сам ресурс хранилища, PVC — заявка пода на него.

Разбор:
- **Deployment** — N одинаковых безымянных подов, любой можно убить/пересоздать, rolling update. Для stateless (веб, API).
- **StatefulSet** — стабильные имена (`kafka-0`), у каждой реплики **свой** диск через `volumeClaimTemplates`, упорядоченные операции. Для БД, Kafka, MinIO.
- **PV (PersistentVolume)** — объект «вот кусок хранилища»: размер, тип доступа, где физически (CSI-драйвер, NFS, локальный диск). Ресурс уровня кластера, создаётся админом или автоматически.
- **PVC (PersistentVolumeClaim)** — объект «поду нужно 10 ГиБ с RWO»: заявка в неймспейсе, которая **биндится** к подходящему PV. Под монтирует именно PVC.
- Связка: **StorageClass** + PVC = динамическое создание PV (CSI-драйвер сам нарезает диск под заявку). Аналогия: PV — квартиры, PVC — заявка на жильё, StorageClass — застройщик, строящий под заявку.

## 2. GET vs POST

**Короткий ответ:** GET — получить ресурс, параметры в URL, идемпотентен и кэшируется; POST — передать данные/создать ресурс, тело в запросе, не идемпотентен.

Разбор по пунктам:
- **Семантика**: GET не должен менять состояние сервера (safe); POST — изменяющее действие.
- **Идемпотентность**: повтор GET безвреден → браузеры/прокси могут ретраить и кэшировать; повтор POST может создать второй заказ → формы переспрашивают «отправить снова?», балансировщики по умолчанию не ретраят POST.
- **Данные**: GET — query string (`?a=1&b=2`), длина ограничена, параметры оседают в логах серверов и истории браузера (секреты в URL — нельзя!); POST — тело запроса любого размера и формата (JSON, файлы).
- И то и то — просто методы HTTP: «GET безопаснее, потому что POST шифруется» — миф, шифрует только TLS, оба одинаково открыты в HTTP.
- Девопс-угол: GET-эндпоинты можно кэшировать на CDN/nginx (`proxy_cache`), POST — нет; health checks делают GET/HEAD.

## 3. git fork vs git pull

**Короткий ответ:** это операции разного уровня. Fork — не команда git, а функция хостинга (GitHub/GitLab): полная копия чужого репозитория в твоём аккаунте. `git pull` — команда git: забрать коммиты из удалённого репозитория и влить в текущую ветку.

Разбор:
- **Fork** нужен, когда у тебя нет прав пушить в чужой репозиторий: форкаешь → клонишь свой форк → коммитишь → открываешь Pull Request в исходный (upstream) репозиторий. Синхронизация форка: добавить `remote` upstream и подтягивать (`git fetch upstream && git merge upstream/main`).
- **`git pull`** = `git fetch` (скачать новые коммиты с remote) + `git merge` (или `git rebase` с флагом `--rebase`) в текущую ветку.
- Бонус, который любят: **fetch vs pull** — fetch только скачивает (безопасно, посмотреть глазами), pull сразу вливает. И **clone vs fork**: clone — локальная копия любого репо; fork — серверная копия под твоим аккаунтом.

## 4. Hardlink vs symlink

**Короткий ответ:** хардлинк — второе равноправное имя того же файла (тот же inode); симлинк — отдельный файл-указатель, хранящий путь.

Ключевое: файл — это inode, имя — запись в каталоге. Хардлинк: та же ФС, нельзя на каталог, файл жив, пока счётчик ссылок > 0. Симлинк: свой inode, работает между ФС и на каталоги, при удалении цели становится битым. Подробный разбор с командами — [Linux-страница, п. 4.1](./linux-baza.html).

## 5. Linux vs Windows (глазами инженера)

**Короткий ответ:** разные ядра, философии и экосистемы: Linux — открытый, модульный, «всё — файл», управление текстом и через SSH; Windows — закрытый, монолитная экосистема Microsoft, управление через GUI/PowerShell/AD.

Что назвать, чтобы прозвучало инженерно, а не «линукс бесплатный»:
- **Философия**: Linux — маленькие композируемые утилиты, конфиги — текстовые файлы, всё скриптуется; Windows — интегрированные подсистемы, конфигурация в реестре/oснастках.
- **ФС**: ext4/xfs (иноды, права ugo+ACL, чувствительность к регистру) vs NTFS (ACL-модель); в Linux «всё — файл» (устройства, сокеты, /proc).
- **Процессы/сервисы**: systemd vs Service Control Manager; fork/exec vs CreateProcess.
- **Пакеты и обновления**: apt/yum из репозиториев vs MSI/Windows Update.
- **Серверная практика**: Linux доминирует в вебе, контейнерах и облаке (контейнеры — это Linux-технология: namespaces+cgroups); Windows Server — там, где AD, Exchange, .NET-легаси, 1С.
- Мост между мирами: WSL2 (Linux-ядро в виртуалке внутри Windows), PowerShell на Linux, .NET кроссплатформенный.

## 6. netstat vs ss

**Короткий ответ:** делают одно и то же (показывают сокеты), но netstat — устаревшая утилита из net-tools, читающая /proc построчно; ss — современная замена из iproute2, получает данные напрямую из ядра через netlink — быстрее и информативнее.

Разбор:
- На системе с сотнями тысяч соединений netstat может работать минуты, ss — мгновенно.
- ss умеет фильтры на уровне ядра: `ss -tnp state established '( dport = :443 )'`, показывает больше TCP-деталей (таймеры, буферы, cwnd).
- Соответствие флагов почти 1:1: `netstat -tulpn` → `ss -tulpn` — переучиваться легко.
- Тот же водораздел: `ifconfig`/`route`/`arp` (net-tools, легаси) → `ip a` / `ip r` / `ip neigh` (iproute2). На собесе говори ss/ip, про netstat — «легаси, знаю, но не использую».

## 7. ReplicaSet vs Deployment vs StatefulSet vs DaemonSet

**Короткий ответ:** все — контроллеры подов, разница — в вопросе, на который каждый отвечает. ReplicaSet: «сколько копий?». Deployment: «сколько копий + как обновлять?». StatefulSet: «копии с именами и своими дисками». DaemonSet: «по одной на каждой ноде».

- **ReplicaSet** держит N живых реплик, и всё. Руками не создаётся.
- **Deployment** = ReplicaSet + версии: новый шаблон пода → новый RS → постепенный перелив реплик (rolling), история для rollback.
- **StatefulSet**: стабильные DNS-имена, PVC на реплику, порядок 0→1→2. Для stateful.
- **DaemonSet**: под на каждой (подходящей) ноде, новая нода — под появляется сам. Агенты: node-exporter, fluent-bit, CNI, kube-proxy.
- Полный разбор — [K8s-страница, пп. 3, 5.1](./k8s-seti-balancery.html).

## 8. Roles vs Playbooks в Ansible

**Короткий ответ:** playbook — исполняемый сценарий («на этих хостах выполнить эти задачи»); role — переиспользуемый модуль-пакет задач со стандартной структурой, который подключается в плейбуки. Плейбук — программа, роль — библиотека.

Разбор:
- **Playbook** — YAML-файл со списком plays: `hosts:` (на ком) + `tasks:` (что сделать). Запускается: `ansible-playbook site.yml`.
- **Role** — каталог со стандартной раскладкой: `tasks/` (задачи), `defaults/` (переменные по умолчанию, самый низкий приоритет), `vars/`, `templates/` (jinja2), `files/`, `handlers/` (рестарты по notify), `meta/` (зависимости). Роль сама не запускается — её подключают: `roles: [nginx, postgresql]`.
- Зачем роли: переиспользование между проектами (Ansible Galaxy — репозиторий готовых ролей), тестируемость (molecule), читаемость — плейбук из 500 строк превращается в `roles: [common, nginx, app]`.
- Практика: плейбуки — тонкие («какие роли на какие группы хостов»), вся логика — в ролях.

## 9. Вызов функции vs системный вызов

**Короткий ответ:** вызов функции — прыжок внутри твоей же программы в user space, стоит наносекунды; системный вызов — обращение к ядру за привилегированной операцией (файлы, сеть, память, процессы) с переключением контекста user→kernel, на порядки дороже.

Разбор:
- Программа не может сама писать на диск или в сеть — железом владеет ядро. Нужен файл? Вызываешь `open()/read()/write()` — специальной инструкцией (syscall) процессор переключается в режим ядра, ядро проверяет права, делает работу, возвращает результат.
- Обычная функция (`strlen`, твоя `calc()`) — просто `call` по адресу в том же адресном пространстве, без смены привилегий.
- Библиотечные функции часто обёртки над syscall: `printf` (форматирование — user space) внутри зовёт `write` (syscall). `malloc` — менеджер в user space, который изредка просит у ядра память через `brk`/`mmap`.
- Посмотреть syscalls процесса: `strace -c ls` (сводка с счётчиками). Дороговизна переключения — причина буферизации: писать по байту = тысячи syscalls; libc копит в буфер и пишет одним `write`.
- Связка с траблшутингом: высокий **%sy** в top = процесс молотит syscalls (мелкие I/O, сеть) — иди со strace/perf.

## 10. Контейнеризация vs виртуализация

**Короткий ответ:** виртуалка эмулирует железо и несёт полную ОС со своим ядром; контейнер — изолированный процесс на общем ядре хоста. VM — сильнее изоляция, контейнер — легче и быстрее.

Таблица для добивок: старт (минуты vs миллисекунды), оверхед (ГБ на гостевую ОС vs мегабайты), плотность (десятки VM vs сотни контейнеров на хост), изоляция (гипервизор vs namespaces+cgroups — эксплойт общего ядра пробивает все контейнеры), миграция (live migration vs пересоздание). Гибриды: Kata Containers, Firecracker — контейнерный UX с VM-изоляцией. Подробнее — [Linux-страница, п. 3.7](./linux-baza.html).

## 11. Привилегированный vs непривилегированный контейнер

**Короткий ответ:** privileged-контейнер (`docker run --privileged`) получает полный доступ к хосту: все capabilities, все устройства `/dev`, отключённые seccomp/AppArmor — фактически root на хосте в обёртке. Обычный контейнер — урезанный: ограниченный набор capabilities, без прямого доступа к устройствам.

Разбор:
- Обычный контейнер, даже с root внутри, — это root с подрезанными крыльями: Docker оставляет ~14 capabilities из 40+ (нет `CAP_SYS_ADMIN`), фильтрует syscalls через seccomp-профиль, не даёт монтировать ФС и грузить модули ядра.
- **--privileged** снимает всё: можно монтировать диски хоста, менять сеть, грузить модули → побег на хост тривиален. Легитимные случаи: Docker-in-Docker в CI, CNI/storage-плагины, отладка. Правило: вместо privileged давать точечные права: `--cap-add SYS_PTRACE`, `--device /dev/fuse`.
- Отдельно не путать (и назвать — плюс): **rootless-контейнеры** — сам демон/рантайм работает не от root (через user namespaces: root внутри контейнера = обычный юзер снаружи). Podman так умеет из коробки.
- K8s-угол: `securityContext: privileged: true` в поде — то же зло; ограничивается Pod Security Standards (baseline/restricted), а лучший дефолт: `runAsNonRoot: true`, `readOnlyRootFilesystem: true`, `capabilities: {drop: [ALL]}`.

## 12. Потоки vs процессы

**Короткий ответ:** процесс — запущенная программа с изолированной памятью; поток — единица выполнения внутри процесса: свой стек, но память и файлы общие с соседями.

Следствия, которые ждут в ответе: общение потоков — общая память, быстро, но нужны локи (race conditions); процессов — только через IPC (pipe, сокеты, shared memory). Падение потока валит весь процесс; падение процесса не трогает другие. Создание потока дешевле. В ядре Linux и то и другое — task (clone() с разными флагами). Подробно — [Linux-страница, п. 2.1](./linux-baza.html).

## 13. Где используется ICMP

**Короткий ответ:** ICMP — служебный протокол сети (L3, живёт внутри IP, портов нет): доставка ошибок и диагностика. На нём работают ping и traceroute.

Разбор по типам сообщений:
- **Echo request/reply (тип 8/0)** — это **ping**: проверка достижимости хоста и RTT.
- **TTL exceeded (тип 11)** — на нём построен **traceroute**: шлём пакеты с TTL=1,2,3…, каждый роутер, обнуливший TTL, отвечает «превышено» — так узнаём весь путь.
- **Destination unreachable (тип 3)** — «хост/порт/сеть недоступны»; его подтип **Fragmentation needed** — основа **Path MTU Discovery**: узнаём максимальный размер пакета до цели. Если файрвол тупо режет весь ICMP — PMTUD ломается, и появляется классический баг «маленькие запросы ходят, большие виснут» (типично за VPN/туннелями).
- **Redirect (тип 5)** — «есть маршрут лучше».
- Практические следствия для собеса: «пингануть порт» нельзя — у ICMP нет портов (порт проверяют `nc -zv host 443`); хост может не отвечать на ping, но работать (ICMP зарезан) — недоступность по ping ≠ хост мёртв; полностью блокировать ICMP — вредно (ломает PMTUD), режут выборочно.
