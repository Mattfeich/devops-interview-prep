# Основы: DevOps как подход, Docker от и до, шифрование vs хэширование

---

## 1. Что такое DevOps?

**Суть для собеса:** DevOps — это не должность и не набор тулов, а подход к разработке, при котором команды разработки и эксплуатации не перекидывают работу через стену, а вместе отвечают за весь жизненный цикл: от коммита до работы в проде. Цель — выкатывать изменения **часто, быстро и надёжно**.

Разжуём через боль, которую он решает. Классическая схема: разработчики пишут код («работает у меня»), швыряют релиз админам, у админов падает, все друг друга обвиняют, релизы раз в квартал, каждый — ночная спецоперация. DevOps ломает эту стену: общая ответственность, автоматизация всего конвейера, маленькие частые изменения (маленькое изменение = маленький риск = легко откатить).

Из чего состоит (модель **CALMS** — удобно рассказать):
- **Culture** — общая ответственность dev и ops, blameless-разборы;
- **Automation** — CI/CD, IaC, автотесты: всё, что повторяется, автоматизировано;
- **Lean** — маленькие партии изменений, быстрый поток;
- **Measurement** — метрики всего (от латенси до частоты деплоев);
- **Sharing** — знания не в головах, а в доках/коде.

Метрики зрелости — **DORA** (назови, это плюс): частота деплоев, lead time (от коммита до прода), change failure rate, время восстановления (MTTR).

**А SRE тогда что?** Частый вопрос. SRE (подход Google) — конкретная инженерная реализация тех же целей: надёжность управляется через SLO и error budget, ручная работа (toil) заменяется кодом. Грубо: DevOps — философия, SRE — «class SRE implements DevOps».

## 2. Waterfall vs Agile vs DevOps (методологии)

- **Waterfall (каскад)**: фазы строго по очереди — требования → дизайн → разработка → тестирование → внедрение; следующая не начинается до конца предыдущей. Плюс: предсказуемость, подходит там, где требования фиксированы (стройка, железо, сертифицируемые системы). Минус: обратная связь в самом конце — узнать, что сделали не то, можно через год; изменения требований ломают всё.
- **Agile** (Scrum, Kanban): работа короткими итерациями (спринты 1–4 недели), после каждой — работающий продукт и обратная связь; требования могут меняться. Scrum — спринты/роли/церемонии; Kanban — непрерывный поток с лимитами WIP.
- **DevOps** — продолжение agile за пределы разработки: agile ускорил написание кода, но релизы всё ещё ждали админов; DevOps доводит итеративность до прода (CI/CD, автоматизация эксплуатации).

Как отвечать на «какой подход лучше?»: смотря на продукт — фиксированные требования и высокая цена ошибки → каскад уместен; продукт развивается и нужна скорость обратной связи → agile + DevOps.

## 3. CI/CD

- **CI (Continuous Integration)**: каждый пуш автоматически собирается и тестируется. Смысл: интеграционные проблемы всплывают через минуты, а не при релизе.
- **CD (Continuous Delivery)**: каждая сборка автоматически доводится до состояния «можно выкатывать» (артефакт + прогон на стейдже); кнопку «в прод» жмёт человек.
- **CD (Continuous Deployment)**: и кнопку жмёт робот — каждый зелёный коммит едет в прод сам.

Типовой пайплайн (расскажи стадиями): lint/статанализ → unit-тесты → сборка артефакта (docker-образ) → скан уязвимостей → пуш в registry → деплой на stage → интеграционные/e2e тесты → деплой в прод (canary/blue-green) → автооткат по метрикам.

Стратегии выката (спрашивают почти всегда):
- **Rolling** — постепенная замена инстансов (дефолт K8s);
- **Blue-green** — два одинаковых окружения, переключение трафика разом, мгновенный откат;
- **Canary** — новая версия получает 1–10% трафика, смотрим метрики, наращиваем;
- **Feature flags** — код выкачен, фича включается рубильником без деплоя.

Инструменты: GitLab CI, GitHub Actions, Jenkins. На вопрос «Jenkins vs GitLab CI» честно: Jenkins — мощный, но требует ухода (плагины, мастера); GitLab CI/Actions — конфиг в YAML рядом с кодом, меньше эксплуатационного бремени.

## 4. GitOps

**Суть:** желаемое состояние инфраструктуры и приложений описано декларативно и лежит в **git**; специальный оператор в кластере (**ArgoCD**, **Flux**) непрерывно сравнивает реальность с git и приводит её к нему. Деплой = merge request.

Ключевое отличие от классического CI/CD-пуша: не пайплайн толкает изменения в кластер (**push**), а агент внутри кластера сам вытягивает их из git (**pull**). Что это даёт:
- git — единственный источник правды: вся история «кто что менял», откат = `git revert`;
- **защита от дрейфа**: руками поправили в кластере → оператор заметит расхождение и вернёт как в git (или подсветит);
- безопасность: кластеру не нужны внешние CI-ключи с правами админа — агент ходит наружу, а не наоборот;
- восстановление кластера = поставить оператор и указать на репозиторий.

Типовая связка на собесе: CI собирает образ и пушит в registry → обновляет тег образа в git-репозитории манифестов (Helm values/Kustomize) → ArgoCD видит коммит и синхронизирует кластер.

## 5. Что такое Docker?

**Суть:** Docker — платформа для упаковки приложения **со всеми его зависимостями** в единый переносимый образ и запуска этого образа изолированным процессом (контейнером) на любой машине с Linux-ядром. Решаемая боль — «у меня работает, у тебя нет»: окружение перестаёт отличаться между ноутбуком, стейджем и продом.

Три кита (объясни каждый):
- **Образ (image)** — неизменяемый снимок ФС с приложением: код, рантайм, библиотеки, до системных пакетов. Собирается по рецепту — **Dockerfile**. Состоит из слоёв (см. страницу Linux, п. 3.8).
- **Контейнер** — запущенный экземпляр образа: обычный процесс хоста, изолированный namespaces (своя сеть, свои PID, своя ФС) и ограниченный cgroups. **Не виртуалка** — ядро общее с хостом (отличия — Linux-страница, п. 3.7).
- **Registry** — хранилище образов (Docker Hub, GitLab Registry, Harbor): `docker push`/`docker pull` — как git для образов.

Жизненный цикл в одну строку: `Dockerfile → docker build → образ → docker push → registry → docker pull → docker run → контейнер`.

Что произносить из внутренностей (вопрос «как докер работает под капотом?»): CLI `docker` → демон `dockerd` → `containerd` (управление жизненным циклом) → `runc` (создаёт процесс с namespaces+cgroups). Поэтому Kubernetes работает без докера — kubelet говорит с containerd напрямую (CRI), а «Docker убрали из K8s» значило лишь удаление прослойки dockershim, образы совместимы (стандарт OCI).

## 6. Что такое Kubernetes и зачем он, если есть Docker?

**Суть:** Docker запускает контейнеры на **одной** машине. Kubernetes — оркестратор: управляет контейнерами на **парке** машин. Ты декларативно говоришь «хочу 5 реплик этого образа с такими ресурсами, доступные по такому адресу» — K8s сам решает, где их запустить, и дальше **непрерывно поддерживает** это состояние.

Что он даёт поверх докера (перечисли — это и есть ответ):
- **Самовосстановление**: контейнер упал / нода умерла → поды пересоздаются в другом месте;
- **Масштабирование**: `replicas: 5` или автоматически по нагрузке (HPA);
- **Балансировка и service discovery**: Service с постоянным DNS-именем над меняющимися подами;
- **Rolling-обновления и откаты** из коробки;
- **Управление ресурсами**: requests/limits, эффективная упаковка контейнеров по нодам;
- **Декларативность**: всё описано YAML-манифестами → хранится в git → GitOps.

Когда K8s НЕ нужен (вопрос-проверка на здравый смысл): пара сервисов на одной-двух машинах — хватит docker compose / systemd; K8s приносит собственную эксплуатационную сложность, которую надо окупать масштабом.

## 7. Dockerfile: инструкции, которые спрашивают

```dockerfile
FROM golang:1.22 AS build        # база (и имя стадии для multi-stage)
WORKDIR /src                     # рабочий каталог (создаст сам; вместо RUN mkdir + cd)
COPY go.mod go.sum ./            # сначала зависимости — ради кэша слоёв!
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

FROM alpine:3.20                 # вторая стадия — чистый лёгкий образ
RUN adduser -D app
USER app                         # не root! (best practice)
COPY --from=build /app /app      # забрать ТОЛЬКО бинарь из стадии build
EXPOSE 8080                      # документация «слушаю 8080» (порт НЕ открывает!)
HEALTHCHECK CMD wget -qO- localhost:8080/healthz || exit 1
ENTRYPOINT ["/app"]              # что запускать
CMD ["--port=8080"]              # аргументы по умолчанию
```

### 7.1 CMD vs ENTRYPOINT — вопрос-фаворит

Оба задают, что выполнится при старте контейнера. Разница — в том, **что происходит с аргументами `docker run`**:

- **CMD** — команда **по умолчанию**: всё, что напишешь после имени образа в `docker run`, **полностью заменяет** CMD.
- **ENTRYPOINT** — **фиксированная** команда: аргументы из `docker run` **дописываются к ней**.
- **Вместе** (канонический паттерн): ENTRYPOINT — исполняемый файл, CMD — дефолтные аргументы, которые пользователь может переопределить.

```
ENTRYPOINT ["/app"]  CMD ["--port=8080"]
docker run img                  →  /app --port=8080
docker run img --port=9090      →  /app --port=9090      # заменился только CMD
docker run --entrypoint sh img  →  sh                    # подменить ENTRYPOINT — только флагом
```

Обязательно скажи про **две формы записи**: **exec-форма** `["bin","arg"]` — процесс запускается напрямую с PID 1 и получает сигналы (SIGTERM при остановке); **shell-форма** `CMD bin arg` — запускается как `/bin/sh -c "..."`, PID 1 — шелл, который **не пересылает SIGTERM** приложению → каждый `docker stop` ждёт 10 секунд и убивает SIGKILL'ом, graceful shutdown не работает. Всегда exec-форма; если нужен шелл-функционал и зомби-жатва — init-процесс `tini` (`docker run --init`).

### 7.2 Остальные пары и ловушки

- **COPY vs ADD**: COPY — просто копирует файлы из контекста сборки; ADD дополнительно умеет распаковывать локальные архивы и качать URL. Правило: **всегда COPY**; ADD — только когда осознанно нужна распаковка tar.
- **ARG vs ENV**: ARG — переменная **времени сборки** (`docker build --build-arg VER=1.2`), в работающем контейнере её нет; ENV — переменная **времени выполнения** (живёт в контейнере, видна приложению). Секреты через ARG/ENV не передавать — остаются в истории образа (`docker history`); для сборки — BuildKit `--mount=type=secret`.
- **EXPOSE** ничего не открывает — это метаданные-документация. Порт наружу публикует только `docker run -p`.
- **RUN vs CMD**: RUN выполняется **при сборке** (создаёт слой), CMD — **при запуске**.
- **VOLUME** — объявляет точку монтирования; данные там переживают контейнер.
- Каждая RUN/COPY — слой; удаление файла следующим слоем размер **не уменьшает** (файл остался в предыдущем слое) — чистить в том же RUN.

### 7.3 Multi-stage builds — зачем

**Суть:** несколько `FROM` в одном Dockerfile: в тяжёлой стадии собираем (компилятор, dev-зависимости, исходники), в финальную лёгкую копируем **только результат** (`COPY --from=build`). В registry и прод едет только последняя стадия.

Что это даёт: образ go-приложения худеет с ~800 МБ (golang + исходники + кэш сборки) до ~15 МБ (alpine + бинарь); меньше поверхность атаки (в проде нет компилятора и исходников); один Dockerfile вместо пары «build.sh + Dockerfile.prod». Стадии можно таргетировать: `docker build --target build` (например, для стадии с тестами в CI).

### 7.4 Docker best practices — чек-лист для ответа

1. **Маленький образ**: multi-stage, slim/alpine/distroless-база, `.dockerignore` (не тащить .git и node_modules в контекст), чистка кэша пакетов в том же RUN.
2. **Кэш слоёв**: редко меняющееся выше, код — последним (см. пример: COPY go.mod до COPY . .).
3. **Не root**: `USER app`; read-only rootfs (`--read-only`) где возможно.
4. **Один процесс — один контейнер**; связка процессов — это уже compose/pod.
5. **Логи в stdout/stderr**, не в файлы внутри контейнера.
6. **Теги**: не деплоить `:latest`; пиновать версии базовых образов (а лучше — digest `@sha256:`), иначе сборка невоспроизводима.
7. **Сигналы**: exec-форма ENTRYPOINT, graceful shutdown по SIGTERM, `tini` при необходимости.
8. **Секреты не в образ** (ни ARG, ни ENV, ни COPY) — только при запуске: env/secret-менеджер/vault.
9. **HEALTHCHECK** и лимиты ресурсов при запуске.
10. **Сканирование** образов (trivy/grype) в CI.

## 8. Дополнения по CI/CD из реальных списков вопросов

- **Артефакт сборки** — неизменяемый результат пайплайна, который дальше только перемещается, но не пересобирается: docker-образ, jar, deb-пакет, бинарь. Принцип «build once, deploy many»: один и тот же артефакт (по digest/версии) проходит stage и едет в прод — гарантия, что тестировали ровно то, что выкатили. Хранятся в registry/Nexus/Artifactory.
- **Секреты в CI/CD**: никогда в git и в логи; хранить в секрет-хранилище CI (masked/protected variables в GitLab, Secrets в GitHub Actions) или внешнем (HashiCorp Vault, cloud secret manager) с короткоживущими токенами (OIDC вместо вечных ключей — CI получает временный токен под конкретный запуск); ограничивать по веткам/окружениям; ротация; маскирование в логах; для K8s — External Secrets Operator / sealed-secrets (шифрованные секреты можно хранить в git).
- **Ansible (push) vs Puppet/Chef (pull)**: Ansible — **push**: управляющая машина по SSH раскатывает состояние, агентов нет; просто начать, но нет непрерывного согласования — дрейф живёт до следующего запуска. Puppet/Chef — **pull**: на каждом хосте агент, который каждые N минут сам приходит к серверу за конфигурацией и приводит хост к ней; постоянная сходимость, но инфраструктура тяжелее (сервер, агенты, сертификаты). Тот же водораздел, что push-CI/CD vs GitOps.

## 9. Шифрование vs хэширование (+кодирование и подписи)

Четыре разные вещи, которые путают — разложи таблицей, это выигрышный ответ:

| Что | Обратимо? | Ключ | Зачем | Примеры |
|---|---|---|---|---|
| **Кодирование** | да, всеми | нет | представление данных (не защита!) | base64, URL-encoding, UTF-8 |
| **Шифрование** | да, владельцем ключа | да | **конфиденциальность** | AES, ChaCha20, RSA |
| **Хэширование** | **нет** | нет | **целостность**, отпечаток | SHA-256, MD5 (мёртв) |
| **Подпись** | проверяема всеми | приватный/публичный | **авторство + целостность** | RSA/ECDSA/Ed25519 |

Разжёвано:
- **Кодирование** — просто другая запись тех же данных. Base64 «расшифрует» кто угодно — поэтому секреты K8s в base64 НЕ защищены (вопрос-ловушка).
- **Шифрование** — данные можно вернуть, зная ключ. **Симметричное** (AES): один ключ шифрует и расшифровывает; быстрое; проблема — как передать ключ. **Асимметричное** (RSA, эллиптика): пара ключей — публичным шифруют, приватным расшифровывают; медленное. На практике — гибрид: асимметрикой обмениваются симметричным ключом, дальше всё шифруют быстрым AES. **Ровно так работает TLS.**
- **Хэширование** — односторонняя функция: из данных любой длины — отпечаток фиксированной длины; из отпечатка данные не восстановить; изменился один бит — хэш другой полностью. Применения: контроль целостности (checksums), дедупликация, git-коммиты, **пароли** — но с нюансом: пароли хэшируют не быстрым SHA-256, а специальными **медленными** функциями с солью (bcrypt, argon2), чтобы перебор был дорог; соль — случайная добавка против радужных таблиц и одинаковых хэшей у одинаковых паролей.
- **Подпись** = «хэш, зашифрованный приватным ключом»: автор хэширует документ и шифрует хэш своим приватным ключом; любой проверяет публичным. Так подписаны TLS-сертификаты (CA подписывает данные сертификата), git-теги, пакеты дистрибутивов (apt/rpm ключи).

Связка с сертификатами (подробно про TLS — Linux-страница, п. 2.6): сертификат = публичный ключ + имя владельца, **подписанные** приватным ключом CA. Доверие строится цепочкой подписей до корневого CA из хранилища ОС. Проверка руками: `openssl s_client -connect host:443`, `openssl x509 -text -noout -in cert.pem`, срок действия — самая частая причина внезапного «всё сломалось» (мониторить экспирацию — blackbox_exporter).

## 10. Облачные модели: IaaS, PaaS, SaaS (и что вокруг)

**Суть:** три модели отличаются тем, **сколько слоёв берёт на себя провайдер, а сколько остаётся тебе**. IaaS — тебе дают «железо» (виртуальные машины, сети, диски), всё остальное твоё. PaaS — тебе дают готовую платформу для запуска кода, ты приносишь только приложение. SaaS — тебе дают готовую программу целиком, ты просто пользователь.

Разжуём через аналогию с пиццей (её реально рассказывают на собесах, она называется «Pizza as a Service»):

- **On-premise** (свой сервер в своей стойке) — готовишь пиццу дома с нуля: твоя мука, твоя духовка, твоя кухня, твой газ. Полный контроль — и полная ответственность за всё, включая сломавшуюся духовку.
- **IaaS** (Infrastructure as a Service) — тебе привезли замороженную пиццу: духовка, газ и стол — провайдера, но разогреваешь, следишь и сервируешь ты. В ИТ: провайдер даёт виртуальные машины, сети, диски, а ОС, обновления, настройка, приложения, бэкапы — на тебе. Примеры: AWS EC2, Google Compute Engine, Yandex Compute Cloud, любой VPS-хостинг.
- **PaaS** (Platform as a Service) — доставка пиццы: тебе привозят готовую, твоё дело — стол и напитки. В ИТ: провайдер даёт готовую среду запуска (рантайм, база, масштабирование, патчи ОС — его забота), ты приносишь только код. Примеры: Heroku, Google App Engine, AWS Elastic Beanstalk; **управляемые базы** (RDS, Cloud SQL) и **managed Kubernetes** (EKS/GKE) — тоже по сути PaaS-слой: control plane обслуживает провайдер.
- **SaaS** (Software as a Service) — пришёл в пиццерию: сел и ешь. В ИТ: готовое приложение по подписке через браузер, ты не управляешь ничем, кроме своих данных и настроек. Примеры: Gmail, Slack, Notion, Zoom, GitHub (как сервис), Datadog.

Таблица «кто за что отвечает» (Т — ты, П — провайдер):

| Слой | On-prem | IaaS | PaaS | SaaS |
|---|---|---|---|---|
| Железо, сеть, датацентр | Т | П | П | П |
| Виртуализация | Т | П | П | П |
| ОС и её патчи | Т | **Т** | П | П |
| Рантайм/middleware | Т | Т | П | П |
| Приложение | Т | Т | **Т** | П |
| Данные и доступы | Т | Т | Т | **Т** |

Обрати внимание на последнюю строку: **за данные и права доступа отвечаешь ты всегда, даже в SaaS** — это называется shared responsibility model («модель разделённой ответственности»), и это любимый уточняющий вопрос: облако отвечает за безопасность *самого облака*, ты — за безопасность *того, что в облаке* (настройки, IAM, открытые наружу бакеты).

Дополнительные модели, которые стоит назвать, чтобы блеснуть:
- **FaaS** (Functions as a Service, serverless) — ещё выше PaaS: ты приносишь не приложение, а отдельную функцию; она запускается только на входящее событие, платишь за миллисекунды выполнения. Примеры: AWS Lambda, Cloud Functions. Плюс: ноль администрирования, идеально для редких/всплесковых задач. Минус: cold start (первый запуск медленный), лимиты времени, привязка к провайдеру.
- **CaaS** (Containers as a Service) — тебе дают запуск контейнеров без управления нодами: AWS Fargate, Cloud Run.
- **DBaaS** — управляемая база данных (RDS, Cloud SQL): частный случай PaaS.

**Как отвечать на собесе** на «в чём разница между IaaS, PaaS и SaaS?»: «Разница — в границе ответственности. IaaS — аренда виртуальной инфраструктуры: машины, сети, диски; ОС и всё выше — моё (EC2). PaaS — готовая платформа: приношу код, платформа сама разворачивает и масштабирует (Heroku, managed-базы, managed K8s). SaaS — готовый продукт по подписке (Gmail, Datadog). Чем выше модель — тем меньше контроля и возни, тем сильнее vendor lock-in. И во всех моделях за данные и настройки доступа отвечает клиент — shared responsibility».
