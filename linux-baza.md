# Linux и сети — база, разжёванная «для чайника»

Здесь — подробные ответы на вопросы из твоего списка + разбор того, как bash обрабатывает команду, + топ-вопросы с реальных собесов. Каждый ответ: сначала суть одной фразой (так и отвечай на собесе), потом подробное объяснение.

## Часть 1. Как bash обрабатывает команду — по полочкам

### 1.1 Что значит «bash парсит»? Это про любую команду?

**Суть:** парсинг — это превращение строки текста, которую ты набрал, в понятную шеллу структуру: «какая команда, какие аргументы, куда вывод». Да, это происходит с **каждой** введённой строкой.

Ты набираешь просто текст: `ls -l /tmp > out.txt`. Для компьютера это пока набор букв. Bash должен понять:

1. **Разбить строку на слова и операторы** (токенизация): `ls`, `-l`, `/tmp` — слова; `>` — оператор редиректа; `|`, `&&`, `;` — тоже операторы. При этом учитываются кавычки: `echo "hello world"` — это ОДИН аргумент `hello world`, а без кавычек — два. Именно поэтому файл с пробелом в имени без кавычек ломает команды.
2. **Понять структуру**: это одна простая команда? Пайплайн (`cmd1 | cmd2`)? Условная цепочка (`cmd1 && cmd2` — второе только при успехе первого)? Цикл?
3. **Выполнить раскрытия (expansions)** — в строгом порядке:
   - фигурные скобки: `file{1..3}.txt` → `file1.txt file2.txt file3.txt`
   - тильда: `~/logs` → `/home/matvey/logs`
   - переменные: `$HOME` → `/home/matvey`
   - подстановка команд: `$(date)` → результат выполнения `date`
   - арифметика: `$((2+2))` → `4`
   - разбиение на слова результатов подстановок
   - glob: `*.log` → список реальных файлов
4. **Снять кавычки** и **настроить редиректы** (`>` — открыть файл, подменить stdout).
5. Только теперь — запустить команду.

Ключевой вывод для собеса: **программа не видит ни кавычек, ни `$VAR`, ни `*`** — она получает уже готовый список аргументов. Всю подготовку делает шелл.

### 1.2 Что значит «разворачивает алиасы»?

**Суть:** алиас — это текстовое сокращение. «Развернуть» — значит подставить вместо сокращения его полный текст, ещё до выполнения.

```bash
alias ll='ls -la'      # создать алиас
ll /tmp                # bash молча превращает это в: ls -la /tmp
alias                  # показать все алиасы
type ll                # "ll is aliased to `ls -la'" — как проверить, что это алиас
unalias ll             # удалить
\ls                    # бэкслеш = выполнить БЕЗ алиаса (если ls заалиашен на ls --color)
```

Важные детали:
- Алиасы живут в конфигах шелла (`~/.bashrc`), у каждого пользователя свои. Новый алиас в `.bashrc` заработает после `source ~/.bashrc` или нового логина.
- Разворачивается только **первое слово** команды, и это тупая текстовая замена — никакой логики.
- В **скриптах алиасы по умолчанию не работают** (только в интерактивном шелле). Нужна логика — пиши функцию:

```bash
mkcd() { mkdir -p "$1" && cd "$1"; }   # функция: принимает аргументы, содержит логику
```

### 1.3 Что такое glob (`*`)?

**Суть:** glob — это шаблоны для подстановки **имён файлов**. Их раскрывает сам шелл, превращая шаблон в список реально существующих файлов.

| Шаблон | Что значит | Пример |
|---|---|---|
| `*` | любое число любых символов | `*.log` → `app.log error.log` |
| `?` | ровно один символ | `file?.txt` → `file1.txt` |
| `[abc]`, `[0-9]` | один символ из набора | `log[12].txt` |
| `**` | рекурсивно по подкаталогам (нужен `shopt -s globstar`) | `**/*.conf` |

Два момента, на которых валят:

1. **Раскрывает шелл, а не программа.** Когда ты пишешь `rm *.log`, программа `rm` никогда не видит звёздочку — bash уже превратил её в `rm app.log error.log access.log`. Следствие: `find / -name *.log` без кавычек сломается, если в текущем каталоге есть .log-файлы — шелл раскроет шаблон раньше, чем find его получит. Поэтому пишут `find / -name '*.log'` — кавычки запрещают шеллу трогать шаблон.
2. **Glob ≠ регулярные выражения.** `*.log` в глобе = «что угодно, потом .log». В regex то же самое пишется `.*\.log`. Это разные языки: glob — для имён файлов в шелле, regex — для grep/sed/awk.

Подвох: если совпадений нет, bash по умолчанию передаёт шаблон **как есть** (программа получит буквально строку `*.log`). Поведение меняется опциями `nullglob`/`failglob`.

### 1.4 Какие переменные bash подгружает и зачем?

**Суть:** переменные — это способ настраивать поведение программ без правки кода. Есть переменные шелла (локальные) и переменные окружения (environment) — последние наследуются запускаемыми программами.

```bash
FOO=bar           # переменная шелла: видна только самому bash
export FOO=bar    # переменная окружения: её увидят и все запускаемые команды
env               # показать всё окружение
echo $FOO         # прочитать
```

Откуда берутся при входе: `/etc/profile` и `/etc/environment` (для всех), `~/.bash_profile`, `~/.bashrc` (твои личные). Ключевые переменные, которые надо знать:

- **`PATH`** — список каталогов через двоеточие, где шелл ищет команды. Набрал `ls` → bash перебирает `/usr/local/bin`, `/usr/bin`… пока не найдёт. «Command not found» = нет в PATH (или вообще).
- **`HOME`**, **`USER`**, **`PWD`** — домашний каталог, имя, текущий каталог.
- **`$?`** — код выхода последней команды (0 = успех). На этом строятся все `if` и `&&` в скриптах.
- **`$$`** — PID текущего шелла, **`$!`** — PID последнего фонового процесса, **`$1 $2 …`** — аргументы скрипта.
- `LANG/LC_*` — локаль, `EDITOR`, `TERM`.

Зачем это всё: приложения читают конфигурацию из окружения (двенадцатифакторные приложения, контейнеры: `docker run -e DB_HOST=...`, K8s `env:` в манифесте — это ровно та же механика).

### 1.5 Что такое builtin?

**Суть:** builtin — команда, встроенная в сам bash. Она выполняется внутри процесса шелла, без запуска отдельной программы (без fork/exec).

```bash
type cd       # cd is a shell builtin
type ls       # ls is /usr/bin/ls  ← внешняя программа
type echo     # echo is a shell builtin (хотя /bin/echo тоже существует!)
```

Builtins: `cd`, `echo`, `export`, `source`, `alias`, `ulimit`, `exit`, `read`…

Почему `cd` **обязан** быть builtin — это вопрос-фаворит. Текущий каталог — свойство каждого процесса. Если бы `cd` был внешней программой, происходило бы так: bash делает fork → дочерний процесс `cd` меняет **свой** каталог → умирает → у bash каталог остался прежним. Дочерний процесс не может изменить состояние родителя. Поэтому всё, что меняет состояние самого шелла (`cd`, `export`, `ulimit`, `source`), встроено в него.

То же самое объясняет разницу `./script.sh` (запуск в новом процессе — его `cd` и переменные умрут вместе с ним) и `source script.sh` (выполнить строки в текущем шелле — изменения останутся).

### 1.6 Потоки и перенаправления — весь блок (`2>/dev/null` и все остальные)

**База.** Когда Linux запускает любой процесс, он выдаёт ему три открытых «канала», пронумерованных числами (это файловые дескрипторы, fd): **0 — stdin** (откуда читать ввод), **1 — stdout** (куда писать нормальный вывод), **2 — stderr** (куда писать ошибки). По умолчанию все три подключены к терминалу. **Перенаправление — это просьба шеллу подключить эти номера к чему-то другому** (файлу, другой команде, мусорке) *до* запуска команды. Сама команда ничего не знает: она честно пишет «в единичку», а куда единичка ведёт — решил шелл.

**Что такое файловый дескриптор вообще.** Это просто **целое число** — «номерок в гардеробе» на открытый ресурс. Когда процесс делает `open("/var/log/app.log")`, ядро находит файл, создаёт запись «открытый файл» (в ней живут текущая позиция чтения и флаги вроде O_APPEND) и кладёт указатель на неё в **таблицу дескрипторов этого процесса** — в первую свободную ячейку. Номер ячейки и есть fd. Нумерация всегда идёт по правилу «наименьший свободный номер»: процесс стартует с занятыми 0/1/2, поэтому первый `open()` вернёт 3, следующий — 4; закрыл 3 и открыл что-то — снова получишь 3.

Три важных факта, которые проверяют на собесе. Первый: дескрипторы **не общие на систему и не на юзера — у каждого процесса своя таблица**: fd 3 у nginx и fd 3 у postgres — совершенно разные вещи (потому и смотрят их по процессу: `ls -l /proc/<PID>/fd`). Второй: через fd в Linux идёт почти всё, а не только файлы — **сокеты, пайпы, epoll, таймеры**; поэтому «Too many open files» у нагруженного сервера обычно означает «слишком много соединений», а не файлов. Третий: уровней на самом деле три — таблица fd (своя у процесса) → общесистемная таблица открытых файлов (позиция, флаги) → иноды. После `fork()` ребёнок получает копию номерков, но они указывают на **те же** записи открытых файлов — родитель и ребёнок двигают общую позицию чтения; а два независимых `open()` одного файла — две независимые позиции.

Лимиты и подсчёт: `ulimit -n` — лимит на процесс (для systemd-сервисов — `LimitNOFILE=` в юните), `fs.file-max` — потолок всей системы, `cat /proc/sys/fs/file-nr` — сколько занято по системе, `ls /proc/<PID>/fd | wc -l` — сколько у конкретного процесса. Ошибки различаются: **EMFILE** — упёрся процесс, **ENFILE** — упёрлась система.

Зачем потока вывода два? Чтобы отделять полезный результат от жалоб: `find / -name '*.conf' 2>/dev/null` — результаты видишь, а тысячи «Permission denied» (они идут в stderr) улетают в мусор.

**Вывод в файл:**
```bash
cmd >  file    # stdout в файл, файл ПЕРЕЗАПИСЫВАЕТСЯ (это 1>, единица подразумевается)
cmd >> file    # stdout в файл, ДОПИСЫВАЕТСЯ в конец
cmd 2> file    # stderr в файл (перезапись); 2>> — дописать
cmd > out.log 2> err.log   # развести потоки по разным файлам
```

**/dev/null** — «чёрная дыра»: устройство, молча съедающее всё записанное. `2>/dev/null` — «ошибки не показывай», `>/dev/null` — «вывод не показывай», `>/dev/null 2>&1` — «замолчи полностью».

**Слияние потоков — `2>&1`:** читается «пусть fd 2 указывает туда же, куда **сейчас** указывает fd 1». Амперсанд обязателен: `2>1` — это «stderr в файл с именем `1`».
```bash
cmd > file 2>&1   # ОБА потока в файл; современное сокращение: cmd &> file (&>> — дописать)
```

**Порядок имеет значение** — перенаправления применяются слева направо:
```bash
cmd > file 2>&1   # 1→file, затем 2→(туда, куда 1)=file. Оба в файле. ✓
cmd 2>&1 > file   # 2→(туда, куда СЕЙЧАС 1)=терминал, затем 1→file.
                  # Ошибки на экране, вывод в файле. Классическая ловушка!
```

**Ввод:**
```bash
cmd < file        # stdin из файла
cmd <<EOF         # here-doc: stdin — всё до строки EOF (многострочный текст прямо в скрипте)
...
EOF
cmd <<< "строка"  # here-string: stdin — одна строка
```

**Пайп — перенаправление в другую команду:**
```bash
cmd1 | cmd2       # stdout первой → stdin второй (stderr в пайп НЕ идёт!)
cmd1 2>&1 | cmd2  # оба потока в пайп; сокращение: cmd1 |& cmd2
cmd | tee file    # tee — «тройник»: и в файл, и дальше на экран/в пайп (-a — дописывать)
```

**Ловушки, которые спрашивают:**
1. **`>` очищает файл ДО запуска команды.** `cat file > file` даст пустой файл: шелл сначала обнулил file (тот самый truncate/O_TRUNC), потом запустил cat — читать уже нечего. Поэтому «отфильтровать файл на месте» через `grep x f > f` нельзя.
2. **`sudo echo 1 > /etc/защищённый` не работает.** Перенаправление делает **твой** шелл до запуска sudo — прав нет у шелла. Правильно: `echo 1 | sudo tee /etc/файл` (tee запущен под sudo и пишет сам).
3. **stderr не идёт в пайп** без явного `2>&1 |` — отсюда «я грепаю ошибки, а грепается пустота».
4. `cmd >/dev/null 2>&1 &` — классическая формула «запусти тихо в фоне», читать её надо уметь.

**Продвинутое (чтобы блеснуть):**
```bash
exec > script.log 2>&1        # с этой строки ВЕСЬ вывод скрипта — в лог (перенаправили сам шелл)
diff <(cmd1) <(cmd2)          # process substitution: вывод команд как «файлы» (/dev/fd/63)
echo ok > /dev/tcp/host/22 && echo "порт открыт"   # bash открывает TCP-сокет как файл — проверка порта без nc
```

И связка с уже разобранным: `ls -l /proc/self/fd` показывает вживую, куда подключены 0, 1, 2 у процесса — тот же механизм, которым мы находили, куда сервис пишет лог.

**Защита от случайного `> file`:**
1. **`set -o noclobber`** — после этого `>` по существующему файлу падает с ошибкой; осознанно перезаписать — специальный синтаксис `>|`; `>>` не трогается. Включают в `~/.bashrc`, защищает интерактивные опечатки.
2. **`chattr +a file`** (append-only атрибут ФС) — файл можно только дописывать: `>>` работает, `>` (truncate) и `rm` запрещены даже root'у, пока атрибут не снят (`chattr -a`, посмотреть — `lsattr`). Идеально для критичных логов. Родственник `+i` (immutable) — вообще никаких изменений.
3. Обычные права записи — защита от чужих; noclobber/chattr — от себя.

**Тонкие моменты, которые спрашивают:**
- **Буферизация.** stderr **не буферизован** (ошибки уходят сразу), stdout — **построчно** в терминал, но **блоками ~4КБ** в файл/пайп. Следствия: в `cmd > f 2>&1` строки могут перемешаться не в порядке печати; `app | grep x` может долго «молчать» — вывод копится в блочном буфере. Лечение: `stdbuf -oL cmd | grep x`, у Python — флаг `-u`.
- **Пайп = подшелл:** `echo hello | read x` — переменная `x` пуста: read выполнился в подшелле и умер вместе с ним. Правильно: `read x <<< "hello"`.
- **Код возврата пайплайна:** `$?` — код **последней** команды (`false | true` → 0!). Все коды — в `PIPESTATUS[@]`; падать при ошибке любого участника — `set -o pipefail`.
- **Кавычки у here-doc:** `<<EOF` — переменные разворачиваются; `<<'EOF'` — всё литерально; `<<-EOF` — срезает ведущие табы (для отступов в скрипте).
- **`cmd < file` vs `cat file | cmd`** — результат тот же, но cat — лишний процесс и подшелл («useless use of cat»).
- **`>` vs `>>` при параллельной записи:** два писателя с `>` затирают друг друга; `>>` (O_APPEND) — ядро гарантирует атомарное дописывание в конец. Поэтому логи — только append.

## Часть 2. Ответы на вопросы из твоего списка

### 2.1 Что такое процессы и потоки? Где они живут?

**Суть:** процесс — запущенная программа со своей изолированной памятью. Поток — «рабочий» внутри процесса; все потоки процесса делят одну память, но каждый выполняет свой код параллельно.

**Процесс** = программа, которую запустили. У него есть:
- своё **адресное пространство** (виртуальная память: код, данные, куча, стек) — другой процесс в неё залезть не может;
- таблица открытых файловых дескрипторов, владелец (uid), рабочий каталог, окружение;
- **PID**. Создаётся через `fork()` (клон родителя) + `execve()` (замена на новую программу). Все процессы — потомки PID 1 (systemd).

**Поток (thread)** = единица выполнения внутри процесса. У потока свои стек и регистры, но **память, файлы, окружение — общие** с другими потоками процесса. Поэтому потокам легко обмениваться данными (общая память), но нужна синхронизация (mutex), иначе race conditions.

**Где живут:** описания и того и другого хранит ядро в своей памяти — структура `task_struct`. Для ядра Linux поток и процесс — почти одно и то же (оба — «task»); поток создаётся `clone()` с флагами «делить память/файлы с родителем». Userspace-часть процесса (его код и данные) живёт в виртуальной памяти, которую ядро маппит на физическую RAM постранично.

Посмотреть: `ps -eLf` (потоки в колонке LWP), `htop` (клавиша H), `ls /proc/<PID>/task/` — каждый поток виден как подкаталог.

Аналогия для ответа: процесс — квартира (свои стены, никто чужой не войдёт), потоки — жильцы этой квартиры (общая кухня-память, но каждый занят своим делом).

### 2.2 Как узнать, какой порт использует процесс?

```bash
ss -tlnp                      # все слушающие TCP-порты + PID/имя процесса
ss -tlnp | grep nginx         # порты конкретного процесса
ss -tnp | grep "pid=1234"     # и установленные соединения процесса
lsof -i -P -n | grep nginx    # то же через lsof
lsof -p 1234 -i               # все сетевые сокеты процесса 1234
```

Обратная задача — какой процесс занял порт (частый практический вопрос «порт занят, кто?»):

```bash
ss -tlnp 'sport = :8080'
lsof -i :8080
fuser 8080/tcp
```

Ключи `ss`: `-t` tcp, `-u` udp, `-l` listening, `-n` не резолвить имена (быстрее), `-p` показать процесс (нужен root для чужих). `netstat` — то же самое, но устарел; на собесе говори `ss`, упомянув «netstat из net-tools — легаси».

### 2.3 Что такое buffer cache?

**Суть:** это кэш дисковых данных в оперативной памяти. Ядро держит в свободной RAM копии прочитанных/записанных файлов, чтобы повторные чтения шли из памяти (наносекунды), а не с диска (миллисекунды).

В `free -h` колонка `buff/cache` объединяет:
- **page cache** — содержимое файлов (основной объём);
- **buffers** — метаданные блочных устройств (суперблоки, inode-таблицы); исторически отдельный кэш, в современных ядрах фактически часть page cache.

Главное, что надо сказать: **это не «занятая» память**. Когда приложению нужна RAM, ядро мгновенно освобождает кэш (чистые страницы просто выбрасываются — на диске есть копия). Поэтому смотрим на `available`, а не `free`. «У тебя 90% RAM в кэше — это плохо?» — нет, это отлично: память работает, а не простаивает. Kafka и MinIO спроектированы в расчёте на page cache.

Запись тоже идёт через кэш: `write()` кладёт данные в память (**dirty pages**) и сразу возвращается; на диск их фоном сбрасывает writeback (или явный `fsync`). Отсюда риск: питание погасло — незаписанное потеряно; поэтому БД делают fsync.

### 2.4 Какие сигналы нельзя перехватить?

**Суть:** два сигнала нельзя ни перехватить, ни проигнорировать, ни заблокировать: **SIGKILL (9)** и **SIGSTOP (19)**. Все остальные процесс может обработать своим хендлером.

Сигнал — это короткое асинхронное уведомление процессу от ядра или другого процесса. Основные:

| Сигнал | № | Что значит | Перехватываемый? |
|---|---|---|---|
| SIGTERM | 15 | «завершись, пожалуйста» (дефолт `kill`) | да — программа может дописать данные и корректно выйти |
| SIGKILL | 9 | убить немедленно | **нет** — ядро просто уничтожает процесс |
| SIGSTOP | 19 | заморозить | **нет** |
| SIGSTOP/SIGCONT | 19/18 | пауза/продолжить | CONT — да |
| SIGHUP | 1 | «терминал отвалился»; демоны часто трактуют как «перечитай конфиг» (nginx reload) | да |
| SIGINT | 2 | Ctrl+C | да |
| SIGCHLD | 17 | ребёнок завершился (родитель должен сделать `wait()` — иначе зомби) | да |

Про `nohup` из твоей скобки: когда ты закрываешь терминал/рвётся SSH, всем процессам этой сессии прилетает SIGHUP, и они умирают. `nohup команда &` запускает процесс с игнорированием SIGHUP — он переживёт закрытие терминала. Современные альтернативы: `tmux`/`screen`, systemd-юнит, `setsid`.

Правильная последовательность остановки сервиса (так и отвечай): сначала SIGTERM, дать время на graceful shutdown, только потом SIGKILL. Именно так поступает Kubernetes: SIGTERM → ждёт `terminationGracePeriodSeconds` (30с) → SIGKILL. И помни из основного гайда: даже SIGKILL не убьёт процесс в D-state, пока тот не вернётся из ядра.

### 2.5 TCP vs UDP — в чём разница и как работают?

**Суть:** TCP — надёжная доставка с установлением соединения (гарантирует «дойдёт, целиком, по порядку», платит скоростью). UDP — просто отправка пакетов без гарантий (быстро, но пакет может потеряться, задублироваться, прийти не по порядку).

**Как работает TCP:**
1. **Установка соединения — 3-way handshake**: клиент → `SYN` («хочу соединиться, мой начальный номер X»), сервер → `SYN-ACK` («принято, мой номер Y»), клиент → `ACK`. Соединение установлено — это состояние на обеих сторонах.
2. **Передача**: каждый байт нумеруется (sequence numbers). Получатель подтверждает приём (`ACK`). Не пришло подтверждение за таймаут → **ретрансмит** (повторная отправка). Пакеты, пришедшие не по порядку, собираются в правильный порядок по номерам.
3. **Контроль потока**: получатель сообщает размер своего окна (сколько готов принять) — быстрый отправитель не завалит медленного получателя. **Контроль перегрузки** (congestion control): отправитель наращивает скорость постепенно и сбрасывает при потерях, чтобы не забить сеть.
4. **Закрытие**: обмен `FIN`/`ACK` с обеих сторон; закрывшая сторона висит в `TIME_WAIT` (страховка от заблудившихся пакетов).

**Как работает UDP:** взял данные, приклеил заголовок (порт источника, порт назначения, длина, чексумма — всё!), отправил. Никаких соединений, подтверждений, повторов, порядка. Приложение само решает, что делать с потерями.

**Кто что использует:** TCP — HTTP(S), SSH, базы данных, Kafka. UDP — DNS (быстрый вопрос-ответ, потерялся — переспросим), DHCP, стриминг/VoIP (старый кадр перепосылать бессмысленно), метрики statsd, VPN (WireGuard), и **QUIC/HTTP3** — надёжность реализована поверх UDP в userspace.

### 2.6 HTTP vs HTTPS

**Суть:** HTTPS — это тот же HTTP, но пропущенный через шифрованный туннель TLS. Даёт три вещи: шифрование (никто по пути не прочитает), целостность (не подменит) и аутентификацию сервера (ты точно говоришь с тем сайтом).

Разворачиваем (и поправляем формулировку из твоей скобки):
- **SSL и TLS** — это не две разные вещи «в составе» HTTPS: SSL — устаревшее название протокола, TLS — его современные версии (актуальны TLS 1.2 и 1.3; SSLv3 мёртв). Говорить «SSL-сертификат» — привычный жаргон, корректно — TLS.
- **Аутентификация, а не авторизация**: сертификат доказывает, что сервер — действительно `example.com` (аутентификация = «ты тот, за кого себя выдаёшь»). Авторизации (прав доступа) в TLS нет — это уровень приложения (логин, токены). Есть **mTLS** — когда и клиент предъявляет сертификат (так общаются сервисы в service mesh).
- **Как работает**: сервер предъявляет сертификат — свой публичный ключ, подписанный **CA** (удостоверяющим центром: Let's Encrypt и т.п.). Браузер проверяет цепочку подписей до корневого CA, которому доверяет ОС. Затем TLS handshake согласует симметричные ключи (в TLS 1.3 — за один round-trip: ClientHello с key share → ServerHello + сертификат + Finished), и дальше весь HTTP-трафик шифруется симметрикой.
- **SNI** — расширение, где клиент называет имя хоста в открытом виде в начале handshake, чтобы сервер с сотней сайтов на одном IP выбрал правильный сертификат.
- Порты: HTTP — 80, HTTPS — 443.

### 2.7 На каких портах и протоколах работают SSH и DNS?

- **SSH — TCP 22.** Только TCP: нужна надёжная упорядоченная доставка для интерактивной сессии.
- **DNS — порт 53, и UDP, и TCP.** Обычные запросы — UDP 53 (быстро, один пакет туда-обратно). TCP 53 используется когда: ответ не влезает в UDP-пакет (флаг truncated → клиент повторяет по TCP), и для **zone transfer** (AXFR, репликация зон между DNS-серверами). Бонус для плюса в карму: DNS over TLS — 853, DNS over HTTPS — 443.

### 2.8 Что такое cgroups?

**Суть:** control groups — механизм ядра, который ограничивает и учитывает ресурсы (CPU, память, диск I/O, число процессов) для **групп процессов**. Это фундамент лимитов Docker и Kubernetes.

Разжуём: обычный процесс может съесть всю память и весь CPU машины. cgroups позволяют сказать: «вот эта группа процессов получает не больше 2 CPU и 4 ГиБ». Ядро само следит: превысил память → OOM kill внутри группы; просит больше CPU → троттлинг (замораживание до конца учётного периода).

- Актуальна **v2**: единое дерево в `/sys/fs/cgroup`, контроллеры `cpu`, `memory`, `io`, `pids`.
- Управление — просто запись в файлы: `echo 4G > /sys/fs/cgroup/mygroup/memory.max`.
- `docker run --memory=512m --cpus=1` и K8s `resources.limits` — это именно записи в cgroup контейнера.
- Посмотреть: `systemd-cgls` (дерево), `systemd-cgtop` (потребление по группам), `cat /sys/fs/cgroup/.../memory.current`.

Пара для полноты картины: **namespaces** изолируют *видимость* (свои PID, сеть, файловая система), cgroups ограничивают *ресурсы*. Контейнер = namespaces + cgroups + слоёная ФС. Никакой магии.

### 2.9 Load Average, экран top, статусы процессов

**Load Average** (три числа — за 1, 5 и 15 минут) — среднее количество процессов, которые **хотят выполняться**: работают на CPU, стоят в очереди за CPU, или (особенность Linux!) висят в непрерываемом ожидании диска (D-state). Простыми словами — длина очереди в магазине: LA=4 на 4 ядрах-кассах — всё занято, но без очереди; LA=40 — очередь. Всегда сравнивай с `nproc`. Три числа дают тренд: 1-мин больше 15-мин — нагрузка растёт; меньше — спадает.

**Экран `top` построчно:**
- Строка 1: uptime, пользователи, load average.
- Строка 2 Tasks: total/running/sleeping/stopped/zombie.
- Строка 3 `%Cpu(s)`: **us** (код приложений) / **sy** (ядро — syscalls, сеть) / **ni** (процессы с пониженным приоритетом nice) / **id** (простой) / **wa** (iowait — ждём диск) / **hi/si** (аппаратные/программные прерывания) / **st** (steal — гипервизор отдал наш CPU соседней виртуалке; >0 на VPS = хостер перепродал ядра).
- Строки 4–5: память и swap (см. buffer cache выше).
- Таблица процессов: **VIRT** (виртуальная память — сколько запрошено адресов, почти бесполезное число) / **RES** (реально занятая RAM — вот на это смотри) / **SHR** (разделяемая — библиотеки) / **S** (статус) / %CPU (может быть >100% — это суммы по потокам, 400% = 4 ядра) / %MEM.

**Статусы процессов:**
- **R** (running/runnable) — выполняется или готов и ждёт CPU;
- **S** (interruptible sleep) — спит в ожидании события (сеть, таймер) — нормальное состояние большинства процессов;
- **D** (uninterruptible sleep) — ждёт I/O внутри ядра, не реагирует даже на kill -9 (подробно — в основном гайде);
- **Z** (zombie) — завершился, но родитель не забрал код возврата через `wait()`; памяти не ест, висит записью в таблице процессов; много зомби = баг родителя;
- **T** (stopped) — остановлен (Ctrl+Z, SIGSTOP);
- **I** (idle) — простаивающие потоки ядра.

### 2.10 Как узнать тип файловой системы раздела?

```bash
df -T                  # смонтированные ФС + тип (самое простое)
lsblk -f               # дерево всех блочных устройств: тип ФС, метки, UUID
blkid /dev/sda1        # тип и UUID конкретного раздела
findmnt /var           # чем и как смонтирован конкретный путь (+опции!)
mount | grep sda1      # то же по-старинке
file -s /dev/sda1      # определить по содержимому (работает даже для несмонтированного)
cat /etc/fstab         # что должно монтироваться при загрузке
```

### 2.11 Как узнать, куда процесс пишет лог?

**Суть:** посмотреть открытые файловые дескрипторы процесса — в `/proc/<PID>/fd/` лежат симлинки на все открытые файлы.

```bash
ls -l /proc/1234/fd            # все открытые fd: 0=stdin, 1=stdout, 2=stderr, дальше файлы
                               # видно: 1 -> /var/log/app.log  или  1 -> pipe:[456789]
lsof -p 1234 | grep -i log     # то же самое читаемо
strace -p 1234 -e trace=write  # реально смотреть, куда идут write() (тяжёлая артиллерия)
```

Если fd 1/2 указывают на pipe/socket — процесс под systemd, и вывод уходит в journald: `journalctl -u имя-сервиса`. Если под контейнером — stdout ловит container runtime: `docker logs` / `kubectl logs`.

## Часть 3. Ещё топ-вопросы с реальных собесов (Linux/сети)

Собрано по спискам реальных собеседований (Хабр «Собеседование Senior DevOps Engineer», подборки 2025–2026).

### 3.1 Как загружается Linux?

Отвечай цепочкой из 5 звеньев:
1. **BIOS/UEFI** — прошивка материнки: инициализирует железо, находит загрузочный диск. Разница: BIOS — легаси, грузит первые 512 байт диска (MBR); UEFI — современный, понимает GPT-разметку и ФС, запускает .efi-файлы с раздела ESP, умеет Secure Boot.
2. **Загрузчик (GRUB2)** — показывает меню, загружает в память ядро и initramfs, передаёт ядру параметры (`root=`, `quiet`…).
3. **Ядро** — распаковывается, инициализирует драйверы и подсистемы, монтирует **initramfs** — мини-ФС в памяти с модулями, нужными чтобы добраться до настоящего корня (драйверы дисков, LVM, RAID, расшифровка LUKS). Зачем initramfs — частый вопрос: ядро не может прочитать корневую ФС, если драйвер для неё лежит на самой этой ФС. Курица и яйцо решаются мини-ФС в памяти.
4. Настоящий корень смонтирован → запускается **PID 1 — systemd**.
5. **systemd** поднимает мир по зависимостям до default target (`multi-user.target` — сервер, `graphical.target` — десктоп; это аналоги старых runlevel 3 и 5). Отладка медленной загрузки: `systemd-analyze blame`, `systemd-analyze critical-chain`.

### 3.2 Модель OSI — и на каких уровнях живут известные протоколы

Семь уровней (снизу вверх): **1 физический** (кабель, сигналы) → **2 канальный** (Ethernet, MAC-адреса, свитчи) → **3 сетевой** (IP, маршрутизация, роутеры) → **4 транспортный** (TCP/UDP, порты) → **5 сеансовый / 6 представления** (на практике схлопнуты) → **7 прикладной** (HTTP, DNS, SSH).

Вопросы-ловушки с собесов:
- **ICMP** (ping, traceroute) — уровень 3: живёт прямо внутри IP, портов у него нет. «Пингануть порт» нельзя — ping проверяет только достижимость хоста; порт проверяют `nc -zv host 443` или `curl`.
- **DNS** — приложение (7 уровень), транспорт — UDP/TCP 53.
- **DHCP** — тоже 7 уровень, UDP 67/68. Как работает — **DORA**: Discover (клиент броадкастит «кто выдаст IP?») → Offer (сервер предлагает) → Request (клиент просит предложенный) → Ack (сервер подтверждает + маска, шлюз, DNS, срок аренды).
- **VLAN** — уровень 2: тег 802.1Q в Ethernet-кадре, режет один физический свитч на изолированные логические сети.
- **ARP** — клей между 2 и 3: «у кого IP 10.0.0.5? скажите ваш MAC».
- **Роутер vs свитч**: свитч — L2, пересылает кадры по MAC-таблице внутри одной сети; роутер — L3, маршрутизирует пакеты по IP **между** сетями.

### 3.3 Как работает DNS-резолвинг (подробно)

Путь запроса `myapp.example.com`:
1. Приложение → библиотечный вызов. Порядок источников определяет **`/etc/nsswitch.conf`** (строка `hosts: files dns` — сначала `/etc/hosts`, потом DNS). Это ответ на вопрос «порядок определения источников разрешения имён».
2. Локальные кэши: systemd-resolved / nscd, у браузеров свой.
3. Не нашли → идём к **рекурсивному резолверу** из `/etc/resolv.conf` (8.8.8.8, резолвер провайдера или CoreDNS в кластере).
4. Резолвер (если у него нет в кэше) раскручивает цепочку: **root-серверы** («.») → «спроси у серверов зоны **.com**» → TLD-серверы .com → «спроси у **авторитативных** серверов example.com» → авторитативный сервер отдаёт запись.
5. Ответ кэшируется на **TTL** секунд на каждом уровне.

Типы записей: **A** (имя→IPv4), **AAAA** (IPv6), **CNAME** (имя→другое имя; не может сосуществовать с другими записями на том же имени), **MX** (почта), **TXT** (проверки владения, SPF/DKIM), **NS** (кто авторитативен за зону), **PTR** (обратная: IP→имя), **SRV** (сервис+порт). Отладка: `dig myapp.example.com`, `dig +trace` (пройти всю цепочку от корня), `dig @8.8.8.8` (спросить конкретный сервер).

### 3.4 Что происходит, когда вводишь URL в браузере? (вопрос-связка всего)

Идеальный ответ соединяет все темы выше — рассказывай цепочкой:
1. Разбор URL → **DNS-резолвинг** (п. 3.3) → получили IP.
2. **TCP** 3-way handshake с IP:443 (п. 2.5).
3. **TLS** handshake: сертификат, проверка цепочки CA, согласование ключей (п. 2.6).
4. **HTTP-запрос** `GET / HTTP/2` с заголовками (Host, Cookie, Accept…).
5. По пути запрос может пройти CDN, L4/L7-балансировщики, reverse proxy (nginx) → приложение → БД.
6. Ответ (статус, заголовки, тело) → браузер парсит HTML, докачивает ресурсы, рендерит.

На каждом шаге интервьюер может «провалиться» глубже — готовься к добивкам «а что если DNS не отвечает / сертификат протух / 502».

### 3.5 Версии HTTP — 1.0 / 1.1 / 2 / 3

- **1.0**: одно TCP-соединение на каждый запрос (дорого — каждый раз handshake).
- **1.1**: **keep-alive** (переиспользование соединения), обязательный заголовок `Host` (много сайтов на одном IP), chunked-передача. Проблема: запросы в соединении строго по очереди — медленный ответ блокирует следующие (head-of-line blocking).
- **2**: бинарный протокол, **мультиплексирование** — много параллельных потоков в одном TCP-соединении, сжатие заголовков (HPACK), server push. Но HOL-блокировка осталась на уровне TCP: потерялся один пакет — стоят все потоки.
- **3**: работает поверх **QUIC (UDP)**: потоки независимы (потеря пакета тормозит только свой поток), TLS 1.3 встроен в handshake (быстрее установка), соединение переживает смену IP (мобильные сети).

### 3.6 Методы и коды HTTP (девопсу — обязательно коды!)

Методы: GET (читать), POST (создать/действие), PUT (заменить целиком), PATCH (частично), DELETE, HEAD (только заголовки), OPTIONS (что разрешено; CORS preflight). **Идемпотентность** (повтор не меняет результат): GET/PUT/DELETE — да, POST — нет (важно для ретраев!).

Коды, по которым девопса гоняют:
- **301 vs 302** — постоянный (кэшируется) vs временный редирект; 304 Not Modified — кэш валиден.
- **401 vs 403** — не аутентифицирован («кто ты?») vs аутентифицирован, но нет прав («тебе нельзя»).
- **429** — rate limit.
- **502 vs 503 vs 504** — вопрос-фаворит про балансировщики: **502** Bad Gateway — прокси получил мусор/отказ от бэкенда (бэкенд упал, connection refused); **503** Service Unavailable — нет живых бэкендов/перегрузка (или осознанный maintenance); **504** Gateway Timeout — бэкенд не ответил за таймаут (завис, медленная БД). Умение по коду сказать «где копать» — маркер практика.

### 3.7 Виртуализация vs контейнеризация

- **Виртуальная машина**: гипервизор (KVM, VMware) эмулирует железо, внутри — **полноценная ОС со своим ядром**. Изоляция сильная, оверхед большой, старт — минуты.
- **Контейнер**: обычный процесс на **общем ядре хоста**, изолированный namespaces (видимость) + cgroups (ресурсы) + слоёная ФС (overlayfs). Оверхеда почти нет, старт — миллисекунды. Изоляция слабее (ядро одно на всех — эксплойт ядра пробивает все контейнеры).
- Следствие: в контейнере не может быть «другого ядра» — образ Ubuntu на хосте CentOS использует ядро CentOS. И Windows-контейнеры на Linux не работают (Docker Desktop гоняет их в скрытой VM).

### 3.8 Docker: образы, слои, оптимизация

- **Образ** — read-only шаблон из **слоёв**: почти каждая инструкция Dockerfile (`RUN`, `COPY`) создаёт слой — diff файловой системы. Слои шарятся между образами (десять образов на базе `ubuntu:24.04` хранят базу один раз) и кэшируются при сборке.
- **Контейнер** = образ + тонкий записываемый слой сверху (copy-on-write). Умер контейнер — слой пропал; персистентность — **volumes**.
- **Кэш сборки**: слой пересобирается, если изменилась инструкция или её входные файлы — и **все слои после него**. Отсюда золотое правило порядка: сначала редко меняющееся (зависимости: `COPY package.json` + `RUN npm install`), потом код (`COPY . .`). Перепутаешь — каждая правка кода будет заново ставить зависимости.
- Уменьшение образа: **multi-stage build** (собрали в тяжёлом образе, в финальный скопировали только бинарь), slim/alpine-базы, `.dockerignore`, объединение `RUN` с очисткой кэша пакетов в том же слое (удаление в следующем слое размер НЕ уменьшает — файл остаётся в предыдущем слое).
- `docker run -p 8080:80` — DNAT-правило: порт 8080 хоста → порт 80 контейнера.

### 3.9 Zombie-процессы и SIGCHLD (частая связка на собесах)

Когда дочерний процесс умирает, ядро шлёт родителю **SIGCHLD** и хранит запись о ребёнке (PID + код выхода), пока родитель не заберёт её вызовом `wait()`. Пока не забрал — ребёнок «зомби» (Z): памяти не ест, но занимает PID. Убить зомби нельзя (он уже мёртв) — можно только починить/перезапустить родителя; если родитель умирает, зомби усыновляет PID 1, который сразу делает wait. Практика в Docker: приложение с PID 1 внутри контейнера, не умеющее wait'ить — накапливает зомби; лечится `docker run --init` (tini).

### 3.10 Forward vs reverse proxy, NAT

- **Forward proxy** — стоит перед **клиентами** и ходит в интернет от их имени (корпоративный прокси, фильтрация).
- **Reverse proxy** — стоит перед **серверами**: клиент думает, что общается с сайтом, а на деле — с nginx, который проксирует на бэкенды. Зачем: TLS termination, балансировка, кэш, сжатие, защита. Подробно — на странице про балансировщики.
- **NAT**: **SNAT/masquerade** — подмена адреса источника (домашний роутер: сотня устройств выходит с одного публичного IP); **DNAT** — подмена адреса назначения (проброс порта внутрь: docker -p, LoadBalancer). Реализуется netfilter/iptables, соединения трекает **conntrack**.

## Часть 4. Ещё из твоего списка: линки, состояние CPU/памяти/диска, файрволы

### 4.1 Hard link vs symlink

**Суть:** хардлинк — ещё одно имя того же файла; симлинк — отдельный маленький файл-указатель, содержащий путь.

Чтобы ответить красиво, начни с инода: **файл — это inode** (структура с метаданными и указателями на блоки данных), а **имя файла — просто запись в каталоге**, которая ссылается на номер инода.

- **Hard link** (`ln файл линк`): вторая запись в каталоге на **тот же inode**. Оба имени полностью равноправны — «оригинала» нет. У инода счётчик ссылок (видно в `ls -l`, вторая колонка); `rm` лишь уменьшает счётчик, данные удаляются, когда он стал 0 **и** файл никем не открыт (вот откуда трюк «удалили лог, а место не освободилось»). Ограничения: только в пределах одной ФС (номера инодов локальны для ФС), на каталоги нельзя.
- **Symlink** (`ln -s цель линк`): отдельный файл со своим инодом, внутри — текстовый путь до цели. Удалил цель → симлинк остался, но **битый** (dangling). Работает через границы ФС, можно на каталоги. `ls -l` показывает `link -> цель`.

Проверить: `ls -li` (номера инодов: у хардлинков одинаковые), `stat файл` (Links: N), `find . -samefile файл` — найти все хардлинки.

**«Но в иноде же только мета — где сам файл?»** Частое недопонимание. Инод хранит не только права/времена, но и **карту блоков данных**: «содержимое лежит в блоках №1000–1050 на диске». Цепочка целиком: `имя (запись в каталоге) → номер инода → инод (мета + карта блоков) → блоки данных`. «Сам файл» — это инод плюс его блоки; имя — просто табличка-указатель. Поэтому `rm` (системный вызов `unlink`) удаляет **только запись имени** и уменьшает счётчик ссылок; блоки данных освобождаются, лишь когда счётчик стал 0 **и** файл никем не открыт. Пока жив хоть один хардлинк — счётчик ≥ 1, данные на месте, файл открывается через второе имя. Информация не терялась, потому что она никогда не жила в имени.

**Как делать линки — основные флаги `ln`:**

```bash
ln  файл  имя_линка       # хардлинк (без флагов)
ln -s цель имя_линка      # симлинк
ln -sf новая_цель линк    # -f: перезаписать существующее имя (типично при деплое: current -> releases/42)
ln -sfn цель линк-на-дир  # -n: заменить сам линк-на-каталог, а не создать цель ВНУТРИ него (классические грабли)
ln -sr ../данные линк     # -r: посчитать относительный путь автоматически
```

Тонкость: путь в симлинке хранится **буквально как текст**, и относительный путь отсчитывается от каталога, где лежит линк, — а не от того, где ты стоял при создании.

**Читаем строку `ls -li` целиком** (флаг `-i` добавляет номер инода первым столбцом):

```
16303  drwxr-xr-x  142  root root  4096  Jun  3 15:28  helm-infra
  │        │        │     │    │     │        │            │
инод   тип+права  ссылки владелец группа размер  mtime      имя
```

Два поля, на которых валятся. **Счётчик ссылок (142):** у файла это число хардлинков, а у каталога — **2 + число подкаталогов**: на каталог ссылаются его имя, его собственная запись `.` и запись `..` из каждого подкаталога. То есть здесь внутри 140 подкаталогов — видно, не заходя. **Размер (4096):** для каталога это размер **самого списка имён** (обычно один блок 4 КБ), а не содержимого; реальный вес — `du -sh каталог`. И mtime каталога меняется при создании/удалении/переименовании записей в нём, а не при правке файлов внутри.

**Смежный вопрос: можно ли восстановить только что удалённый файл?** Корзины нет, `rm` — сразу unlink. Шансы по убыванию: (1) если файл **ещё открыт каким-то процессом** — восстановление стопроцентное: `lsof +L1` → найти PID и fd → `cp /proc/PID/fd/N /tmp/спасённый`; (2) если никто не держит — блоки лишь помечены свободными, но пока не перезаписаны: **немедленно прекратить запись** на раздел (`mount -o remount,ro`), затем на ext4 — `extundelete`/`ext4magic` по размонтированному разделу, универсально — `photorec` (ищет по сигнатурам, но теряет имена); на XFS undelete практически нет. (3) Взрослый ответ для собеса: «восстановление после rm — лотерея, поэтому — бэкапы, снапшоты (LVM/btrfs/ZFS), конфиги в git».

### 4.2 Как быстро оценить состояние CPU, памяти и диска (разжёванно)

Это «джентльменский набор» — на собесе часто просят: «зашёл на тормозящий сервер — покажи руки». Полная методология и разбор метрик — в основном гайде (блок 5); здесь — что запускать и **на что именно смотреть глазами**:

**CPU:**
```bash
uptime          # load average — сравни с числом ядер (nproc)
top             # %Cpu(s): us — приложения, sy — ядро, wa — ждём диск, st — сосед-виртуалка ворует
mpstat -P ALL 1 # по ядрам: одно ядро 100%, остальные спят = однопоточный затык или прерывания
pidstat 1       # кто именно ест
```
Читаем: высокий **us** — профилируй приложение; высокий **sy** — море syscalls (сеть? логи?); высокий **wa** — иди смотреть диск; **st** > 0 — проблема у гипервизора, а не у тебя; всё низкое, а LA высокий — D-state, снова диск/NFS.

**Память:**
```bash
free -h         # смотри available (не free!) и Swap used
vmstat 1        # колонки si/so: не нули постоянно = система свопится = деградация
ps aux --sort=-rss | head   # топ едоков по реальной памяти (RSS)
dmesg -T | grep -i oom      # а не приходил ли OOM killer
```

**Диск:**
```bash
df -h           # место; df -i — иноды
iostat -x 1     # r/s, w/s (IOPS), rkB/s wkB/s (поток), await (латенси!), aqu-sz (очередь)
iotop           # кто именно пишет/читает
du -xsh /* 2>/dev/null | sort -h   # куда делось место
lsof +L1        # удалённые, но открытые файлы (место "утекло")
smartctl -a /dev/sda        # здоровье самого диска
```
Читаем: **await** растёт при том же трафике — диску плохо или он перегружен; `%util` 100% на NVMe — ещё не приговор (параллелизм); место есть, а писать нельзя — иноды или lsof +L1.

**Кто сколько потребляет — по процессам и сервисам** (аналог `kubectl top`, но для обычной машины):

```bash
ps aux --sort=-%cpu | head -15   # топ процессов по CPU (разово)
ps aux --sort=-rss  | head -15   # топ по памяти
pidstat 1                        # по процессам в динамике (-r память, -d диск, -t потоки)
systemd-cgtop                    # «top по сервисам»: CPU/память/IO каждого systemd-юнита
systemctl status nginx           # строки Memory: и CPU: — сколько съел сервис целиком
nethogs                          # топ по СЕТЕВОМУ трафику процессов
iftop                            # трафик по соединениям/хостам
```

`systemd-cgtop` работает потому, что systemd кладёт каждый сервис в свою cgroup — потребление считается на сервис **со всеми дочерними процессами**, а не на один PID (то же можно прочитать руками: `/sys/fs/cgroup/system.slice/nginx.service/memory.current`, `cpu.stat`).

**История — «а кто съел CPU ночью?»:** `atop` как сервис пишет снапшоты каждые 10 минут — `atop -r /var/log/atop/atop_YYYYMMDD`, листаешь по времени клавишами `t`/`T`; `sar` (sysstat) — исторические метрики системы целиком; по-взрослому — node_exporter + process-exporter в Prometheus.

Логика ответа на собесе: **система целиком** (top, vmstat, iostat, free) → **виновник** (pidstat, iotop, nethogs, systemd-cgtop) → **история** (atop, sar, Prometheus).

### 4.3 iptables, nftables, firewalld — как это всё соотносится

**Суть:** файрвол в Linux — это подсистема ядра **netfilter**. iptables и nftables — два поколения инструментов управления ею, firewalld — надстройка-менеджер поверх них.

**Как работает iptables** — модель «таблицы → цепочки → правила»:
- **Таблицы** по назначению: `filter` (пускать/не пускать — собственно файрвол), `nat` (подмена адресов), `mangle` (правка пакетов).
- **Цепочки** — точки на пути пакета через ядро: **INPUT** (пакет адресован этой машине), **FORWARD** (транзит через нас как роутер), **OUTPUT** (мы отправляем), плюс **PREROUTING** (до решения о маршрутизации — здесь DNAT) и **POSTROUTING** (после — здесь SNAT/MASQUERADE).
- Пакет идёт по цепочке **сверху вниз** до первого совпавшего правила; действие: ACCEPT, DROP (молча выбросить), REJECT (выбросить и сообщить), либо прыжок в другую цепочку. Не совпало ничего — применяется **политика цепочки** (default policy).
- **conntrack** — трекинг соединений: правило `-m state --state ESTABLISHED,RELATED -j ACCEPT` пускает ответный трафик уже разрешённых соединений — на нём держится любой stateful-файрвол.

```bash
iptables -L -n -v --line-numbers        # посмотреть filter
iptables -t nat -L -n -v                # посмотреть NAT
iptables -A INPUT -p tcp --dport 22 -s 10.0.0.0/8 -j ACCEPT   # разрешить SSH из внутренней сети
iptables -A INPUT -p tcp --dport 22 -j DROP
```

**nftables** — современная замена (в ядре с 3.13): один инструмент `nft` вместо зоопарка iptables/ip6tables/arptables, свой язык правил, эффективнее на больших наборах (sets/maps вместо линейного перебора), атомарная замена правил. В современных дистрибутивах команда `iptables` — это чаще прослойка `iptables-nft`, которая транслирует старый синтаксис в nftables (проверить: `iptables -V` → `(nf_tables)`). Синтаксис для узнавания:

```bash
nft list ruleset
nft add rule inet filter input tcp dport 22 ip saddr 10.0.0.0/8 accept
```

**firewalld** — демон-менеджер (RHEL/CentOS-мир), сам пишет правила в nftables (раньше — в iptables). Даёт человеческие абстракции: **зоны** (public, internal, trusted — интерфейс/источник приписывается зоне) и **сервисы** («ssh» вместо «tcp/22»), плюс runtime vs permanent конфигурация:

```bash
firewall-cmd --get-active-zones
firewall-cmd --zone=public --add-service=https --permanent   # навсегда (после reload)
firewall-cmd --reload
firewall-cmd --list-all
```
(В Ubuntu-мире аналогичная надстройка — ufw.)

Как собрать в один ответ: «netfilter — механизм в ядре; iptables — классический инструмент (таблицы/цепочки/правила, stateful через conntrack); nftables — его современная замена, куда всё мигрировало; firewalld/ufw — удобные менеджеры поверх. На K8s-нодах руками файрвол не трогаем без понимания — kube-proxy и CNI сами генерируют тысячи правил» — последняя фраза сразу связывает тему с кубом и звучит по-взрослому.

Важный практический нюанс из этого: **Docker сам пишет DNAT-правила в netfilter** (`-p 8080:80`) — и эти правила срабатывают **до** INPUT-цепочки, поэтому опубликованный докером порт может торчать наружу в обход твоего UFW/firewalld. Классическая дыра, отличный факт для собеса.

### 4.4 Как найти и завершить процесс, занимающий порт

```bash
ss -tlnp 'sport = :8080'      # кто слушает 8080 (покажет pid=...)
lsof -i :8080                 # то же
fuser -k 8080/tcp             # найти И убить одной командой (шлёт SIGKILL!)
kill <PID>                    # правильно: сначала SIGTERM (graceful)
kill -9 <PID>                 # не помогло — SIGKILL
```

Правильный порядок озвучь отдельно: найти → понять, что это за процесс (`ps -fp PID` — вдруг это чей-то прод!) → SIGTERM → подождать → SIGKILL. Сразу `kill -9` — минус балл: процесс не успеет дописать данные/закрыть соединения.

### 4.5 Права доступа: chmod, chown, umask

**Модель:** у файла — владелец (**u**ser), группа (**g**roup) и все остальные (**o**ther); каждому — три бита: **r**(4) чтение, **w**(2) запись, **x**(1) выполнение. `rwxr-xr--` = 754.

```bash
ls -l file            # -rwxr-xr-- 1 matvey devs ...
chmod 644 file        # rw-r--r-- (числами)
chmod u+x,g-w file    # символьно: владельцу +выполнение, группе -запись
chown matvey:devs file  # сменить владельца и группу (только root)
chgrp devs file
```

Нюансы, по которым отличают понимающего:
- Для **каталога** биты значат другое: `r` — прочитать список имён, `w` — создавать/удалять файлы в нём (удаление файла — операция над каталогом, не над файлом!), `x` — войти/пройти сквозь (без x не открыть файл даже по точному пути).
- **umask** — маска прав по умолчанию для новых файлов: из базовых прав (файлы 666, каталоги 777) **вычитаются** биты umask. umask 022 → файлы 644, каталоги 755. Задаётся в профиле шелла/systemd-юните.
- Спецбиты: **setuid** (4xxx, исполняемый файл работает от владельца — так `passwd` пишет в /etc/shadow), **setgid** на каталоге (новые файлы наследуют группу каталога — общие каталоги команд), **sticky bit** (1xxx на каталоге — удалять файлы может только их владелец; классика — `/tmp`, `drwxrwxrwt`).
- Дальше базовой модели: ACL (`setfacl/getfacl`) — права конкретным пользователям сверх ugo; capabilities — дробление прав root (`cap_net_bind_service` — слушать порт <1024 без root; так nginx-контейнеры живут без рута).
